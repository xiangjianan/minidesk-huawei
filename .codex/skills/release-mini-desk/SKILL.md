# 发布 Mini Desk 定制版

目标是 `/Users/xiangjianan/github/minidesk-huawei` 及其 `origin` GitHub 仓库。调用本技能表示用户要求发布；执行前读取该仓库的 `AGENTS.md`，检查当前分支、工作区、远程地址和实际仓库，避免误发布到上游。不得部署网站或修改上游仓库。

1. 获取 `origin` 的最新 main 和标签。仅以目标 GitHub 仓库的正式版本标签确定最新版本，不把本地缓存的上游标签、预发布标签或其他仓库的标签混入。按数值比较 `X.Y.Z` 版本，允许可选的 `v` 前缀；在最新正式版本的补丁号上加一，例如 `1.1.19` → `1.1.20`。沿用目标仓库现有标签格式；当前定制仓库使用不带 `v` 的版本号。如果没有可辨认的版本、同一版本存在冲突标签、目标标签或 Release 已存在，停下说明，不要覆盖或强推。
2. 确保准备发布的 `main` 与 `origin/main` 没有未处理的远程提交，且工作区没有无关的未提交改动或未完成的合并。不可用 stash、reset、强推或覆盖来消除分叉或用户改动；无法安全继续时说明。
3. 检查并同步项目中实际使用的版本字段，包括 `package.json`、`package-lock.json`、`index.html` 和 `src/state/version.ts`。根据上次发布以来的真实差异编写精简说明；不要虚构功能。如果代码已是目标版本就保留；如果版本高于目标版本或其他状态存在歧义，不要降级，停下说明。将必要版本变更提交到 main。
4. 对准备发布的确切提交运行适当的测试和 `npm run build`；必须在必要检查通过后发布。构建产物不要提交到 Git。打包为 `dist.<版本号>.zip`，例如 `dist.1.1.20.zip`，压缩包顶层必须是 `dist/`，里面是构建输出（例如 `dist/index.html` 和 `dist/assets/`）。可在仓库根目录用 `zip -r <包路径> dist`，在临时目录保存包，用 `unzip -l <包路径>` 检查压缩包列表、用 `unzip -t <包路径>` 检查完整性，确认解压后目录结构和版本一致。
5. 将发布提交正常推送到目标仓库的 `main`，基于该提交创建并推送对应的新 tag，然后在明确指定的目标仓库创建 GitHub Release，附上编译好的 ZIP 压缩包和基于实际差异的发布说明。使用明确的仓库参数，避免 GitHub CLI 选择 upstream。每个外部步骤后核对结果；如已存在同名资源或操作失败，停止并报告已完成的步骤，不覆盖现有发布资产或标签。GitHub 自动提供的源码包并非上传的附件，无需尝试删除。

完成后核对远程 tag 指向发布提交、Release 和附件名称，报告版本、Release 链接、下载链接、验证结果以及未完成事项。不自动同步上游主仓库；如果用户同时要求同步，先执行同步并验证再发布。
